# Практическая работа №1 — вариант 17

Модель данных в памяти для `Member`, `Query`, `Response`; далее — RPC
поверх TCP и тестирование на основе модели. Данные не сохраняются на диск.

## Этап 1: модель

Записи представлены `NamedTuple`, то есть кортежами с именованными полями.
`Query.member` ссылается на `Member.identifier`, а `Response.query` — на
`Query.identifier`. Несуществующие ссылки и удаление записи, на которую
ссылаются, вызывают `ModelError`. Идентификаторы не переиспользуются.

| Сущность | Функции |
| --- | --- |
| Member | `create_member`, `get_members`, `update_member`, `delete_member` |
| Query | `create_query`, `get_queries`, `update_query`, `delete_query` |
| Response | `create_response`, `get_responses`, `update_response`, `delete_response` |

`select_recent_responses` реализует полное внешнее соединение Query и
Response по `Query.identifier = Response.query`, отбирает строки с
`Response.datetime >= now - 420` и возвращает `argument`, `cache_hit`,
`status`. Время — целое число секунд Unix. Если оно не передано при
создании записи, используется текущее. `now` в выборке можно указать
явно для воспроизводимой проверки граничного случая. Как в реляционной
проекции, одинаковые строки результата выводятся один раз. Query без
Response отбрасывается фильтром по `Response.datetime`.

## Интерактивный режим

Команда: `make install`, затем `make repl`. Каждая строка состоит из
имени функции и необязательного JSON-объекта аргументов. `help` выводит
функции; `exit` завершает работу. `make repl-demo` воспроизводит все
13 операций и ошибку удаления связанной записи в интерактивном режиме.

```text
> create_member {"ip":"127.0.0.1","locale":"ru","platform":"Linux","datetime":1000}
{"identifier": 1, "datetime": 1000, "ip": "127.0.0.1", "locale": "ru", "platform": "Linux"}
> create_query {"argument":"x","member":1,"description":"demo","executing":0}
> create_response {"output":"ok","status":"done","exception":"","query":1,"cache_hit":0,"duration":2}
> select_recent_responses
> delete_member {"identifier":1}
Ошибка: Нельзя удалить Member со связанными Query
```

Если `datetime` не указан, значение зависит от времени запуска.

## Этап 2: RPC поверх TCP

Запуск: `make server` в одном терминале, затем `make demo` в другом.
`RpcClient` можно использовать из своего Python-кода. Параметры функций
и имена его 13 методов совпадают с функциями модели. Результаты клиента
приходят из JSON как словари и списки словарей. Ошибки сервера
вызывают `RpcError` у клиента.

Настройки сервера и демонстрации: `RPC_HOST` (по умолчанию `127.0.0.1`)
и `RPC_PORT` (по умолчанию `5017`). Сервер записывает каждый принятый
запрос отдельной JSON-строкой в `journal.log`; файл исключён из Git.

| Сообщение | Поле | Смещение | Размер |
| --- | --- | ---: | ---: |
| Запрос | версия | 0 | 1 байт |
| Запрос | код операции | 1 | 1 байт |
| Запрос | длина JSON-тела | 2 | 5 байт |
| Запрос | JSON-тело | 7 | по длине |
| Ответ | длина JSON-тела | 0 | 4 байта |
| Ответ | код операции | 4 | 1 байт |
| Ответ | JSON-тело | 5 | по длине |

Числа в заголовке передаются в порядке байтов от старшего к младшему.
Версия протокола — `1`. Коды операций — от `1` до `13` в порядке
функций таблицы выше, затем `select_recent_responses` под кодом `13`.
JSON-тело запроса — объект именованных аргументов, например
`{"identifier": 1}`. Ответ содержит `{"result": ...}` либо
`{"error": {"type": "ModelError", "message": "..."}}`. Один вызов
может передаваться несколькими частями TCP; `read_exact` собирает
ровно указанное число байтов. Максимальный размер тела — 1 МиБ.

```python
from src.client import RpcClient

with RpcClient() as client:
    member = client.create_member("127.0.0.1", "ru", "Linux")
    print(client.get_members())
    client.delete_member(member["identifier"])
```

## Этап 3: тестирование на основе модели

`make test` запускает `pytest` и `RuleBasedStateMachine` из Hypothesis,
затем печатает отчёт `coverage` с ветвями. `make lint` проверяет стиль
Python. Тестовая модель хранит простые словари и собственные счётчики
идентификаторов, поэтому не использует реализацию модели приложения для
вычисления ожидаемых результатов. Hypothesis генерирует создание,
редактирование и удаление записей, изменение ссылок, ошибочные запросы
и проверяет состояние после каждого шага. Начальная цепочка из трёх
сущностей обеспечивает проверку выборки ровно на границе семи минут.
Отдельный тест проверяет чтение сообщений TCP по одному байту.

Проверенный результат `make test`: 2 теста прошли; покрытие по ветвям
составило 98% для `model.py`, 92% для `client.py`, 81% для `protocol.py`,
76% для `server.py` и 89% суммарно. Все 13 функций модели и все 13
методов клиента были вызваны тестом `RuleBasedStateMachine`; непокрытые
строки модели относятся только к двум проверкам неверного типа поля.
